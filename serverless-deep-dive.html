🔥 Warm-Up Polls (no wrong answers — vote, then discuss)

Poll 1: A small website gets 3 visitors a day. Its server runs 24/7. Roughly what share of that server's life is spent actually serving someone?

Three short visits a day is well under 1% utilization — yet a traditional always-on server bills for 100% of the month. That gap between capacity you rent and work you actually do is the entire economic argument for serverless. Today we price that gap precisely.

Poll 2: “Serverless” means…

Your code absolutely runs on servers — in the provider's data centers. Serverless means the servers stop being your job: no provisioning, no patching, no capacity planning. You ship a function; the provider runs it when an event arrives and scales it up or down to zero.

1 “Serverless” Still Has Servers

The one-sentence version

Serverless = you rent executions, not machines. In Session 3 you rented virtual machines by the hour whether they worked or slept. In Session 10 you built services that wait behind an API. Here, the unit shrinks again: a single function — one small piece of code — that the provider starts when an event occurs, runs just long enough to finish, then tears down. No event, no run, no charge.

Tap each card to flip it over:

Myth: “No servers”Reality: servers exist — the provider owns, patches, and scales them. You stopped seeing them, not using them.
Myth: “Always free”Reality: you pay per request plus per fraction-of-a-second of memory used. Cheap at spiky, low volume; it can cost more than a VM at heavy, steady volume.
Myth: “Functions remember things”Reality: functions are stateless. Any run may start in a fresh environment. Memory, carts, and sessions live in a database or cache — never in the function.
Myth: “It replaces everything”Reality: functions have short maximum runtimes (often ~15 minutes) and startup quirks. Long jobs, steady firehoses, and persistent connections still belong on containers or VMs.

🧭 Where this sits in the course: Session 10's SOA lesson said “build small, loosely coupled services that talk over the network.” A function is that idea taken to its limit — a service so small it only exists while it's answering.

2 Functions & Triggers: Anatomy of an Event-Driven App

Every serverless app has the same three bones

1 · The event (trigger). Something happens: an HTTP request arrives, a file lands in storage, a timer fires, a row is added to a database, a message enters a queue.
2 · The function. Your code runs in a fresh, right-sized environment, does one job, returns a result.
3 · The managed services around it. Storage, databases, queues, and identity — all operated by the provider, all billed per use, all connected by events instead of by servers you babysit.

Event sourceTypical function jobCourse connection
HTTP request (API)Answer one endpoint: place order, fetch tourSession 10 · REST & SOA
File uploaded to storageThumbnail it, scan it, transcribe itSession 5 · object storage
Timer (cron)Nightly cleanup, morning reportSession 11 · operations
Database changeSend the confirmation emailSession 6 · collaboration
Queue messageProcess one job at a time, retry on failureSession 9 · reliability

The discipline that makes it work: one function, one job, no memory of the last run. The moment a function needs to “remember,” that memory moves into a database, a cache, or object storage — the same state stores you met in Week 2, now doing double duty.

Drill 1 · The sleepy endpoint

An endpoint runs 500,000 times a month, 100 ms each, at 128 MB (0.125 GB). Using the teaching prices, the monthly bill is closest to…

Answer: A. ✔ Duration: 500,000 × 0.1 s × 0.125 GB = 6,250 GB-seconds × $0.0000167 ≈ $0.10. Requests: 500,000 × $0.0000002 = $0.10. Total ≈ $0.20. ✘ B/C/D are each 10×/100×/1000× slips — the classic error is pricing the requests as if each one cost $0.20 instead of a million of them costing $0.20.

Drill 2 · The busy API

A product API runs 2,000,000 times a month, 200 ms each, at 256 MB (0.25 GB). Monthly bill?

Answer: B. ✔ Duration: 2,000,000 × 0.2 s × 0.25 GB = 100,000 GB-seconds × $0.0000167 ≈ $1.67. Requests: 2 × $0.20 = $0.40. Total ≈ $2.07 — still less than the $12 always-on VM, and this API is doing real work. ✘ A forgot the request charge is per-million (2 million = $0.40, not $0.04). ✘ C/D repeat the 10× slip from Drill 1.

4 Cold Starts, Limits, and When to Say No

The cold start

When a function hasn't run for a while, the provider must prepare a fresh environment before your code starts — downloading it, booting the runtime, running your setup code. That first request pays a cold start (often a few hundred milliseconds; more for heavy runtimes); quick follow-ups reuse a warm environment and skip it. The fixes are boring and effective: keep the package small, lazy-load heavy libraries inside the handler instead of at startup, and keep setup code minimal. Paying for “always warm” capacity exists — and quietly converts your serverless bill back into a server bill, so reach for it last.

Know the walls before you build

LimitTypical shapeWhat it rules out
Maximum runtime~15 minutes per runLong renders, big migrations, model training
StatelessnessFresh environment any runCarts/sessions held in local variables
Cold startsFirst request after idle is slowerHard real-time, latency-critical paths (without mitigation)
Cost crossoverPer-request billing never sleepsSteady 24/7 firehoses — a VM/container wins on price

Rule of thumb: spiky, short, and event-shaped → function. Long, steady, or stateful → container or VM. Most real systems are a hybrid, which is exactly what your course project already taught you to design.

5 🎓 Worked Walkthrough — The Upload Pipeline, Priced Step by Step

The job: Pelican Tours customers upload a photo with each booking. Every upload needs a thumbnail for the tours page. Volume: 40,000 uploads a month, arriving in bursts around weekend promotions. Work through it exactly as you would on the job — every number shown, nothing skipped.

Step 1 · Name the event

The trigger is “a file landed in storage.” No server polls a folder; the storage service itself announces each upload. Event-driven design starts by naming the event in one sentence — if you can't, you don't have a function yet, you have a program looking for a home.

Step 2 · Write the smallest function that does the job

One function: read the uploaded image, produce a 300-pixel thumbnail, save it beside the original, done. It remembers nothing between runs; the storage bucket is the memory. Measured on real uploads: 800 ms average. We configure 512 MB of memory — image work is memory-hungry, and on this pricing model more memory also buys proportionally more CPU, so the run gets shorter as well as roomier.

Step 3 · Convert one run into GB-seconds

512 MB = 0.5 GB. One run: 0.5 GB × 0.8 s = 0.40 GB-seconds. This single number is the atom of every serverless estimate — get it right and the rest is multiplication.

Step 4 · Price one run

Duration: 0.40 × $0.0000167 ≈ $0.0000067. Request: $0.20 ÷ 1,000,000 = $0.0000002. One thumbnail ≈ $0.0000069 — about seven millionths of a dollar. Notice the shape: at this size the duration is 97% of the cost, so optimizing run time beats optimizing request counts.

Step 5 · Scale to the month

40,000 × $0.0000069 ≈ $0.28 a month. The always-on alternative — a small VM waiting all month for weekend bursts — is ~$12 whether it thumbnails 40,000 photos or four. Serverless wins here not because it's fashionable, but because the workload sleeps: most of the month, there is simply nothing to bill.

Step 6 · Argue the other side (always do this)

If uploads grew 100× and arrived steadily all day, the same math gives ~$28/month and climbing, while the VM stays ~$12 — the crossover from Lab A. And the 800 ms thumbnail is safely inside the runtime limit, but a 45-minute video render would hit the wall and belong on a container. The walkthrough's real deliverable isn't $0.28; it's the habit: event → GB-seconds → unit price → monthly → argue the opposite. That five-beat argument is your template for every “should this be serverless?” question you will ever be asked.

🧠 AI Concept of the Day — AI Inference Is an Event

Look at the shape of an AI chatbot call: a prompt arrives, the model thinks for a few seconds, an answer streams back, silence. That is exactly the function shape — short, stateless, spiky, billed per use (per token, Session 1). It's no accident that model APIs are sold the way functions are billed: both sell executions, not machines.

So the modern pattern is a matryoshka: your function calls the model API. A customer message (event) wakes your function, your function sends the prompt to a hosted model, the answer returns per-token, your function saves the conversation to a database (because functions remember nothing) and replies. You pay twice in the best way: per request for your code, per token for the model's thinking — and $0 for every hour nobody chats. The one job that never fits this shape: training or fine-tuning, which runs for hours to days on GPUs. That's renting machines (Session 3's IaaS), and no event trigger will save it.

📝 Session Quiz — Serverless Story Problems

Eight workplace scenarios — the last two test today's AI concept. Pick the best answer; every question explains all four options after you answer. Counts toward the syllabus “Exercises/Quizzes” grade (30%).

Q1 · The Saturday stampede

A bakery's ordering API sits nearly idle Monday–Friday, then takes 50× traffic for three hours every Saturday morning. The owner is tired of paying for a server that's bored all week. Why do functions fit this workload so well?

Answer: C. ✔ Spiky + short + stateless is the function sweet spot: capacity appears per request at the stampede and vanishes (with the bill) on Tuesday. ✘ A — a function on a cold start can be slower; speed isn't the selling point. ✘ B — storage is a separate managed service with its own per-use bill. ✘ D — functions are stateless, so the order database matters more, not less.

Q2 · The 45-minute render

A videographer wants one function to transcode each client's 45-minute video. The platform caps a single function run at about 15 minutes. What's the right call?

Answer: B. ✔ A hard runtime wall is an architecture signal, not an obstacle to outsmart: long, continuous work belongs on containers/VMs (Lab B sorted exactly this). ✘ A — splitting helps only if the tool supports chunked processing with merged output; as stated it produces three unrelated partial files. ✘ C — memory buys CPU speed, not permission; a faster 45-minute job is still a long job, and you'd pay premium rates the whole way. ✘ D — destroying the product to fit the platform inverts every priority from Session 12.

Q3 · Price it before you pitch it

Your manager asks what the Drill 2 API (2,000,000 runs/month, 200 ms, 256 MB) costs as functions versus the $12 always-on VM. Using the teaching prices, your answer is…

Answer: D. ✔ 2,000,000 × 0.2 s × 0.25 GB = 100,000 GB-s ≈ $1.67, plus 2 × $0.20 = $0.40 → $2.07. ✘ A/B are the 100×/10× decimal slips from the drills — always sanity-check against the VM price. ✘ C forgets duration entirely; at longer runtimes duration is most of the bill (Step 4 of the walkthrough).

Q4 · The sleepy first click

Testers report: “The page is fast all day, except the very first visit each morning takes two extra seconds.” The app is functions behind an API. Best first move?

Answer: A. ✔ That's a textbook cold start, and package size + startup work is where most of it lives. ✘ B throws away the pay-per-use economics over a known, mitigable quirk. ✘ C is not an engineering answer. ✘ D works but bills like a server — it's the last resort, not the first move (Segment 4).

Q5 · The vanishing cart

A developer stores each shopper's cart in a variable inside the function. In testing it works; in production, carts randomly empty. Why?

Answer: C. ✔ It's the flip-card myth from Segment 1, live in production. Warm environments sometimes reuse memory — which is why it “worked in testing” — but nothing guarantees it. ✘ A is conspiracy, not architecture. ✘ B wouldn't be random per-run on the server side. ✘ D confuses capacity with persistence; memory size doesn't make an environment permanent.

Q6 · Name that trigger

“Every time a customer uploads a booking photo, a thumbnail appears on the tours page a second later — including at 3 AM, with nobody watching.” Which design produces exactly that?

Answer: B. ✔ It's the walkthrough verbatim: the storage event is the trigger — instant, automatic, and billed only per upload. ✘ A fails “3 AM, nobody watching.” ✘ C does the work thousands of times for zero new uploads and slows every page view. ✘ D is the always-on pattern serverless replaces — a machine billing all night to check an empty folder.

Q7 · The chatbot's two meters (AI concept)

A tour company adds AI support chat: traffic is unpredictable, each reply calls a hosted model billed per token, and some nights nobody writes in at all. Why is wrapping the chat endpoint in a function a sound design?

Answer: C. ✔ Both meters only run while someone is chatting — the matryoshka from today's AI section. ✘ A — functions serve inference; training is a different shape of job entirely (Q8). ✘ B — the token bill is the model's price; your function just stops adding an idle-server bill on top of it. ✘ D — no such rule; choose the shape because the economics fit.

Q8 · Three days on GPUs (AI concept)

A team wants to fine-tune a model on their support tickets: one continuous job, roughly three days, needs GPUs throughout. A teammate proposes “just make it a function — it's AI, so it's serverless, right?” Your response?

Answer: A. ✔ Training is long, steady, stateful, GPU-shaped — every wall in Segment 4 at once. Inference is the event; training is the factory. ✘ B repeats the “AI = serverless” confusion the AI section dismantled. ✘ C chains straight into runtime caps, lost state, and premium per-second pricing. ✘ D — the cloud rents GPUs precisely so laptops don't have to do this (Session 3).
